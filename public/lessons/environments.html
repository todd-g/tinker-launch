Where does the code actually run?

A 10-minute lesson on three environments — your laptop, every pull request, and production — and how Vercel + Convex + Git fit together without anyone stepping on anyone else's data.

01 The three lanes

Every change you make travels along one of three lanes. Each lane has its own frontend, its own database, and its own URL. Nothing leaks between them.

Your hunch, refined

You guessed Local → preview Convex, Staging → staging Convex, Prod → prod Convex. The shape is right, but the middle lane is better thought of as Preview — one isolated backend per PR, not one shared staging environment. Convex has first-class support for this via Preview Deployments. (If you genuinely need a long-lived shared staging too, you can add it — covered in §4.)

03 Git, mapped to lanes

One branch model handles all three. Trunk-based: main is always deployable, every change goes through a short-lived feature branch and a PR.

main
→ Production deploy on merge
feat/x
→ Vercel Preview + Convex Preview
Spun up on first push. Each push redeploys.
your laptop
→ Your dev Convex + localhost
Lives until you stop npx convex dev.

Rules of the road

  • main is sacred — it ships to prod. No direct pushes.
  • Branch from main, name it feat/, fix/, or chore/.
  • Open the PR early (even as draft) — that's what gives you a Preview URL to share.
  • Keep branches short — under a week. Long branches grow expensive merge conflicts and stale preview data.
  • Squash-merge to main. One PR = one commit on the trunk.
  • Reviews on the Preview URL, not on screenshots.

"But what about a real staging?"

You probably don't need one. The PR preview is staging — a real Vercel build, a real Convex backend, isolated data, shareable URL. If you do need a stable long-lived environment (QA team, demo to stakeholders, integration partner testing):

  • Add a staging branch in Git, protected like main.
  • Provision a second Convex project named yourapp-staging (or use a long-lived preview deployment).
  • In Vercel, point the staging branch at that backend via a custom env.
  • Flow: feat/x → main → staging (cherry-pick or fast-forward when ready to QA).

Start without it. Add it only when a specific person is blocked without it.

04 Wait — where's the gate before prod?

This is the question everyone asks moving off staging. The honest answer: yes, the latest main goes straight to prod on merge. But the single "staging gate" you're used to didn't disappear — it split into three cheaper, more targeted checks that run continuously.

The mental shift

Old model: one gate (staging) tries to catch everything before the deploy. Modern model: the deploy itself is cheap and reversible, so the gates move around the deploy instead of in front of it.

The three gates that replaced staging

GateWhat it catchesWhen it runs
1. PR preview"Does this PR work in isolation?"Every push to a branch
2. Merge queue"Does main + this PR still pass CI?" Catches two PRs that work alone but conflict when both land.At merge time
3. Observability + rollback"Did the deploy regress anything?" Vercel instant rollback + Convex schema compat = bad deploys reversed in ~30s.Continuous, post-deploy

What this means day-to-day

  • Deploys are small and frequent. Ship to prod whenever main is green. Small reversible deploys beat big rare ones.
  • main is the integration branch. Staging used to be "stuff we're about to ship, working together" — main is that now. Merge queue keeps it honest.
  • The blast radius of a bad deploy is small. Errors visible in minutes, rollback in one click. That's what makes the no-staging model safe.
  • Risky changes get a human on the preview URL. Not just CI green — an actual teammate clicks through the risky paths on the PR's preview before you merge. Cheap, surprisingly effective.

When you genuinely still want long-lived staging

Don't fight the team if any of these apply:

  • QA or product team that needs a stable URL to test against without PR churn
  • External integration partners who need a fixed non-prod endpoint
  • Compliance environments (SOC 2 evidence, HIPAA, audit trails)
  • Heavy data migrations you want to rehearse against a prod-shaped, stable dataset

For most small product teams on Vercel + Convex, the four gates above replace staging entirely. Add it the day a specific person is blocked without it — not before.

05 Wiring the pipeline

How a git push ends up with the right Vercel preview pointing at the right Convex preview — it comes down to one build command and three deploy keys.

The build command (do this once)

In Vercel → Project → Settings → General → Build Command, change it to:

npx convex deploy --cmd 'npm run build'

This single line is the glue. On every Vercel build, it:

  1. Reads CONVEX_DEPLOY_KEY from Vercel's build env.
  2. Detects whether the key is prod: or preview: scoped.
  3. For prod: deploys functions + schema to the production Convex deployment.
  4. For preview: spins up (or reuses) a Convex preview deployment named after the git branch.
  5. Sets NEXT_PUBLIC_CONVEX_URL into the build env, pointed at the deployment it just touched.
  6. Runs npm run build — Next.js bakes that URL into the bundle.

The three deploy keys

One-time setup, per project

Easy path: install the official Convex Vercel integration from the Vercel marketplace. It plumbs the deploy keys automatically — no copy-paste. Recommended.

Manual path:

  1. Convex dashboard → Settings → URL & Deploy Key → generate a preview deploy key (starts with preview:).
  2. Same screen → generate a prod deploy key (starts with prod:).
  3. Vercel → Project → Settings → Environment Variables:
    • Add CONVEX_DEPLOY_KEY = preview key, scope: Preview only
    • Add CONVEX_DEPLOY_KEY = prod key, scope: Production only
  4. Vercel → Project → Settings → General → set the Build Command (above).
  5. Confirm convex is in dependencies in package.json (not only devDependencies) — Vercel needs it at build time.
The one rule

Never set NEXT_PUBLIC_CONVEX_URL directly in Vercel's env UI. Let convex deploy set it. Hardcode it and every preview points at the same backend — exactly the isolation you're trying to gain.

Seeding preview deployments

By default a fresh Convex preview starts empty — correct schema, zero rows. To seed it on creation, extend the build command:

npx convex deploy --cmd 'npm run build' --preview-run 'seed:initial'

The seed:initial function runs against the new preview backend right after it's created and before the build finishes. Good for: fixture users, demo content, baseline records the UI assumes exist.

Wait, where does npm run build actually run?

Vercel's build infrastructure. Not GitHub Actions, not your laptop. The flow:

  1. You git push. GitHub fires a webhook to Vercel.
  2. Vercel spins up an ephemeral build container in its own cloud.
  3. That container clones the repo, runs npm install, then runs your Build Command.
  4. convex deploy (running inside the container) makes an API call to Convex's servers — "here's the new backend code, deploy it."
  5. npm run build (also inside the container) compiles the Next.js bundle.
  6. The compiled output ships to Vercel's edge network to serve.

Mental model

Nothing ever runs on your laptop after a git push. Your local dev is one thing; the deployed environments are entirely Vercel + Convex's cloud, glued together by that one build command.

Verifying it's wired right

  1. Push a feature branch.
  2. Wait for Vercel's preview to deploy. Click the URL.
  3. Open the Convex dashboard — confirm a preview deployment named after your branch exists.
  4. On the live preview, DevTools → Network. Convex requests should go to the preview URL, not prod.
  5. Make a write in the preview UI. Confirm it lands in the preview Convex dashboard, not in prod.

If step 5 ever shows data in prod, stop and re-check your env-var scoping before pushing anything else.

Are Vercel and Convex actually in sync?

Pretty much. The build command pins both halves to one git commit, deployed in one step. The exact sequence on a prod deploy:

  1. Convex deploys the backend (functions + schema) first.
  2. Vercel runs npm run build with the new URL injected.
  3. Both succeed → new frontend goes live alongside the new backend.
  4. Anything fails → the whole build fails, Vercel keeps serving the old frontend.

The one wrinkle: there's a ~10-30 second window during step 2 where the new Convex backend is already live but the old frontend is still serving. That's safe only if your schema changes are backwards-compatible — the old frontend has to keep working against the new backend.

Expand-then-contract

For breaking schema changes (rename a function, remove a field, tighten validation), split it across three PRs: (1) Expand — add the new shape, old code still works. (2) Migrate — code now uses the new shape; backfill old data. (3) Contract — remove the old shape, safely. Cheap deploys stay cheap for backwards-compat changes only.

Same logic applies to rollback: Vercel's "Instant Rollback" reverses the frontend, not Convex. For alpha-scale, the practical move is fix forward — push a PR that reverts the breaking change rather than trying to roll back. Backwards-compat habits make this painless.

07 The five mistakes we want to avoid

  1. Pointing local Next.js at prod Convex. One bad mutation = real users affected. Your .env.local should never contain a prod URL.
  2. Sharing one Convex dev deployment across the team. Each developer runs npx convex dev to get their own. Stomping on each other's seed data wastes hours.
  3. Testing migrations only in dev. Prod data has shapes dev never sees. Run the migration against a Preview deployment with prod-shaped seed data before merging.
  4. Long-lived branches. A week-old branch has a week-old preview database. Either it's stale or you re-seeded — either way, it's not testing what main will look like.
  5. Committing .env.local or deploy keys. Use Vercel's env UI. Use git secret-scan in CI.
